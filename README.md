# Career Fit

A mobile-friendly, no-login, no-database MVP that estimates:

1. **Career Fitness** (0–100) — pick your target IT role (Full Stack, Java Backend, Frontend, Python Backend, DevOps/Cloud, Data Engineer, QA Automation, Cloud Engineer, Network Engineer, or Cybersecurity Engineer — each with a paired Lead track), check off the tech stack you know against what that role's market expects, and get a role-specific score. The score-calculation details are intentionally not shown in the UI — only the score and the recommendation.
2. **Financial Fitness** — emergency-fund coverage (in months) from savings and essential monthly expenses.

Recommendations are generated by the Grok (xAI) API using the user's role, known/missing tech stack, and scores as context, with a fixed rule-based recommendation (naming the specific missing technologies) used automatically if the Grok call fails or times out. A **"Call for 1-to-1 Advice"** button (`tel:` link) is always available. Nothing is persisted — no login, database, cookies, or local/session storage; state resets on reload.

## Quickstart

```bash
npm install
cp .env.example .env   # fill in VITE_GROK_API_KEY, VITE_GROK_API_URL, VITE_CONTACT_PHONE
npm run dev            # http://localhost:5173
```

## Scoring rubric

**Career readiness** (weights sum to 100, capped): tech-stack match against the selected role's expected market stack (0–40), relevant experience (0–15), certifications/education relevance (0–10), network/job-search activity (0–10), adaptability/reskilling willingness (0–10), plus a **fixed, role-specific market-demand rating** (0–15, defined per role in [itRoles.js](src/modules/itRoles.js) — e.g. DevOps/Cloud is rated 15/15 "very high demand", QA Automation is rated 9/15 "moderate demand"). Because market demand is fixed per role rather than self-rated, a role's maximum achievable score reflects its real ceiling (e.g. QA Automation maxes at 94, not 100) — this is intentional and shown transparently in the results breakdown. Update `itRoles.js` as the job market and expected stacks shift.

**Financial fitness**: `months = savings / essential monthly expenses`; bands: `<1` Critical, `1–2` At Risk, `3–5` Adequate, `6+` Strong. Score = `min(100, months / 6 * 100)`.

## Hosting: GitHub Pages (quick, free, public URL)

A workflow at [.github/workflows/deploy-pages.yml](.github/workflows/deploy-pages.yml) builds and deploys `dist/` to GitHub Pages automatically on every push to `main`.

1. In your GitHub repo, go to **Settings → Pages** and set **Source** to **GitHub Actions** (one-time setup).
2. (Optional, for Grok/tel: features) Go to **Settings → Secrets and variables → Actions** and add repo secrets `VITE_GROK_API_KEY`, `VITE_GROK_API_URL`, `VITE_CONTACT_PHONE` — the workflow passes them into the build. Skip this if you're fine with the offline rule-based recommendations and no call button for now.
3. Push to `main`. The workflow builds, tests, and deploys automatically; the Actions tab shows progress and the live URL once done.
4. Your site will be available at `https://<your-username>.github.io/<your-repo-name>/`. `vite.config.js` auto-detects the repo name from GitHub Actions so asset paths resolve correctly — no manual `base` path edits needed.

Note: like the Grok API-key risk described below, anything in `VITE_*` secrets is still baked into the public client bundle at build time — GitHub Actions secrets only keep the value out of your source code/logs, not out of the deployed site.

## Hosting: private S3 + CloudFront (manual steps)

This is a static site with no server-side component — deploy the `dist/` folder behind CloudFront with the S3 bucket kept fully private.

1. **Create a private S3 bucket** (block all public access left ON):
   ```bash
   aws s3 mb s3://<your-bucket-name>
   aws s3api put-public-access-block --bucket <your-bucket-name> \
     --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
   ```
2. **Create a CloudFront distribution** with the bucket as origin, using **Origin Access Control (OAC)** (in the CloudFront console: Origins → Create Origin → S3 origin type → Origin access control settings → create/select an OAC). Set the default root object to `index.html`.
3. **Update the bucket policy** to allow only the CloudFront distribution (via OAC) to read objects — CloudFront's console offers a "copy policy" button after creating the OAC that generates this automatically:
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Sid": "AllowCloudFrontServicePrincipal",
       "Effect": "Allow",
       "Principal": { "Service": "cloudfront.amazonaws.com" },
       "Action": "s3:GetObject",
       "Resource": "arn:aws:s3:::<your-bucket-name>/*",
       "Condition": {
         "StringEquals": { "AWS:SourceArn": "arn:aws:cloudfront::<account-id>:distribution/<distribution-id>" }
       }
     }]
   }
   ```
4. **Build and deploy**:
   ```bash
   npm run build
   aws s3 sync dist/ s3://<your-bucket-name> --delete
   aws cloudfront create-invalidation --distribution-id <distribution-id> --paths "/*"
   ```
5. (Optional) Attach a custom domain + ACM certificate to the CloudFront distribution and enforce HTTPS-only viewer protocol policy.

## Known limitations / roadmap

- **Grok API key exposure (accepted risk for MVP)**: `VITE_GROK_API_KEY` is baked into the client-side JS bundle and the Grok API is called directly from the browser. Anyone can extract the key from the built bundle or network tab and use it outside this app. This was a deliberate, informed MVP trade-off to avoid standing up a backend. **Before scaling beyond MVP validation**, replace direct browser calls with a minimal serverless proxy (e.g. a Lambda Function URL) that holds the key server-side.
- No authentication, database, or persisted user history by design — every session starts fresh.
- Modular structure (separate scoring, financial, recommendation, and Grok-client modules) is intentional so future phases can add authentication, persistent storage, server-side AI, and scheduling without rewriting the core scoring logic.
